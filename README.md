A churn model is easy. The parts around it are what decide whether anyone can
use it: a **point-in-time feature store** that cannot see the future, **leakage
screens** that run before every training, a **threshold derived from business
economics** rather than F1, a **promotion gate that refuses a model which is
better on average and worse for mid-market accounts**, and monitoring that
reports drift now and accuracy sixty days late, because that is when the truth
arrives.

> ### ⚠️ Synthetic data, no deployment
>
> **Vertex Systems does not exist.** Every account, invoice, support ticket and
> usage row is generated by `polaris simulate` in this repository. No model here
> has scored a real customer and nothing has been deployed to a production
> environment. The measurements below are real measurements of real code on
> simulated data — that distinction is the point.

## The problem

Vertex Systems is a B2B SaaS company with 3 000 customers. Roughly a quarter of
them leave over two years, and a customer success team of a handful of people
can work a list of maybe a hundred accounts a fortnight. They need that list.

The naive version of this project is a notebook that reports ROC-AUC 0.99 and
cannot be used. Three reasons, all of which are handled here:

**The features see the future.** Computing "days to renewal" from a column the
source system only fills in for accounts that renewed makes the model brilliant
and useless. This happened in this repository: the first model scored 0.995.

**The label does not exist yet.** A 60-day horizon means the most recent 60 days
of history have features and no label. Training on them as negatives teaches the
model that "has not churned yet" means "did not churn".

**A better average is not a better model.** Gradient boosting here beats
logistic regression overall and is worse on mid-market accounts. Whether that is
acceptable is a business decision, and it should be made by someone who can see
it — not hidden inside an aggregate metric.

---

## Objectives

- One implementation of every feature, shared by training, serving, monitoring
  and the notebooks.
- Correct-by-construction point-in-time data, checked empirically rather than
  assumed.
- A threshold computed from the cost of a retention play and the margin on a
  saved account.
- A promotion path a model can **fail**, with an exit code a scheduler can read.
- Predictions logged with the model version, the threshold and the explanation
  that was shown to a human.
- Every claim in this README reproducible with the commands in section 10.

## Features

| | |
| --- | --- |
| **Point-in-time feature store** | 33 features, one row per `(reference_date, account_id)`, strict `<` on every date comparison, label `NULL` until the horizon elapses |
| **Feature contract** | one Python declaration drives training, serving, drift and this README; CI reconciles it against the DDL |
| **Leakage screens** | value AUC, missingness AUC **and** lift, plus a rebuild-stability check; a `LEAK` is a non-zero exit |
| **Temporal split with embargo** | one full horizon between train, validation and test |
| **Calibrated probabilities** | isotonic, cross-fitted inside the training split |
| **Economic threshold** | break-even probability from margin, cost and success rate; chosen on validation |
| **Experiment tracking** | MLflow (params, metrics, artefacts) plus an `ml.training_run` row that survives MLflow being down |
| **Model registry** | stages, one production version enforced by a partial unique index |
| **Promotion gate** | six checks, per-segment regression with a minimum-evidence rule, recorded `--force` |
| **Scoring API** | FastAPI, in-process model, group-based explanations, every prediction logged |
| **Monitoring** | PSI against frozen training bins, prediction drift between scoring runs, label-lagged live performance in euros |
| **Operations** | 14 CLI commands, exit codes 0/1/2/3, non-root container, five-job CI |

## Database setup

`polaris simulate` creates the schemas if they are missing and then generates the
business. The DDL is idempotent (`CREATE TABLE IF NOT EXISTS` throughout), so
running it against a populated database does not destroy anything.

```bash
polaris simulate       # schemas + 24 months of simulated history
polaris reset --yes    # drop the schemas (asks first without --yes)
```

Three schemas: `saas` (the simulated source), `features` (the store), `ml`
(runs, registry, predictions, evaluations, drift baselines). Schema names are
configuration and are validated against `^[a-z_][a-z0-9_]*$` before they are
interpolated into SQL, because a schema name cannot be a bound parameter.

## Usage

The whole lifecycle, which is also what CI runs:

```bash
polaris simulate                                  # the business
polaris build-features                            # point-in-time features
polaris screen                                    # leakage screens; non-zero on LEAK
polaris train --algorithm logistic --promote      # baseline, shipped
polaris train --algorithm gradient_boosting       # challenger, registered only
polaris promote 2                                 # through the gate; exit 3 if refused
polaris score --limit 3000 --explain              # scores + explanations, all logged
polaris monitor                                   # drift now, performance when labels land
```

Inspection: `polaris doctor`, `features --show`, `models`, `runs`.
One-shot: `polaris cycle` (train → register → promote if allowed → score).
Serving: `polaris serve`. Everything has `--help`.

Exit codes: `0` success, `1` handled failure, `2` misuse, **`3` blocked by a
gate** — a refused promotion is not a crash, and a scheduler must be able to
tell the difference without parsing text.

## Point-in-time features

Every row answers one question: *what was knowable about this account on this
date?* Three mechanisms enforce it.

1. **Strict `<` on every date comparison.** A ticket opened on the reference
   date is not knowable at the start of that day. One `<=` is a one-day leak,
   which is enough to lift the metric and small enough that nobody questions it.
2. **`days_to_renewal` is computed from `signup_date` plus the contract term**,
   never read from a column the source system fills in only for renewals.
3. **`label_known_at`.** The label is `NULL` until `reference_date + horizon` has
   actually elapsed, so the most recent 60 days carry features and no label.

The strongest check is a test rather than an argument: rebuild a past reference
date after new data has arrived, and every feature value must be identical. If it
changes, that feature was reading the future.

Contract and windows: [`docs/features.md`](docs/features.md).

## Leakage screens

`polaris screen` runs before every training. A `LEAK` verdict exits non-zero and
fails CI.

| Screen | Catches | Thresholds |
| --- | --- | --- |
| value | one feature that nearly *is* the label | `LEAK` ≥ 0.95 AUC, `REVIEW` ≥ 0.90 |
| missingness | a feature whose *presence* predicts the label | `LEAK` at AUC ≥ 0.80 **or** lift ≥ 8×, over groups of 200+ |
| stability | a past reference date whose features change | any change is blocking |

The missingness screen needed the lift criterion to work. 59.4 % of accounts
legitimately have no renewal date — monthly contracts — and that dilutes a real
leak's AUC into the `REVIEW` band where it gets ignored. The label-rate lift
between missing and present is not diluted: on a frame where the date is missing
for exactly the churners it runs into the thousands; the legitimate case in the
real store sits at 3.4× and stays a `REVIEW`, which is the right verdict for
something a human should look at once.

The value threshold is high (0.95, not 0.80) on purpose: usage decline is a
genuinely strong signal — the strongest single feature in the store reaches an
AUC of 0.873 on its own — so a lower bar would cry wolf on exactly the features
the model is supposed to rely on.

## The decision threshold

Not F1. Three business numbers:

```
act on an account:  worth  9 000 € × 0.30 − 350 € = 2 350 €   if it would have churned
                    costs                   350 €             if it would not

break-even          p* = 350 / (9 000 × 0.30) = 0.130
```

Below 13 % predicted risk the play loses money in expectation. The operating
threshold is then chosen on the **validation** split as the point maximising
total expected value — which put the production model at 0.1162. Changing the
cost of a CSM call changes the threshold and requires no retraining.

This is also why calibration is part of the model: an expected value computed
from an uncalibrated score is arithmetic on a number that does not mean what it
says.

## The promotion gate

Six checks, each existing because of a way a model can look better than it is:

| Check | Passes when |
| --- | --- |
| `feature_version` | the model's contract version matches the store's |
| `beats_champion` | PR-AUC gain ≥ 0.005 (skipped, visibly, for the first model) |
| `no_segment_regression` | no **evaluable** segment drops by more than 0.03 |
| `calibration` | test Brier ≤ 0.12 |
| `latency` | measured p95 single-row prediction ≤ 50 ms |
| `positive_expected_value` | expected value per 1 000 accounts > 0 at the chosen threshold |

The segment check is the one worth reading. Measured here, gradient boosting is
better overall (PR-AUC 0.3155 vs 0.2856) and **worse on mid-market** (0.2392 vs
0.2629). At the default 0.03 tolerance the promotion is allowed; at 0.01 the
identical promotion is refused:

```
BLOCKED no_segment_regression: 2 segment(s) judged;
regressions: mid_market 0.2392 vs 0.2629 (-0.0237);
not evaluable (under 20 positives): enterprise
$ echo $?
3
```

**"Not evaluable" is not "pass".** The enterprise segment has 4 churns in the
test split; the difference between two PR-AUCs computed from 4 positives is
noise, and a gate that blocks on noise gets switched off within a month. So a
segment is judged only above 20 positives, and the ones below are named in the
output rather than silently skipped.

`--force` exists — an incident, a rollback, a regression the business has
accepted — and it is a named flag that logs a warning and writes the failed
checks onto the model version. Exactly one version serves at a time, enforced by
a partial unique index rather than by application code.

Full reasoning: [`docs/promotion.md`](docs/promotion.md).

## Serving

```bash
polaris serve --host 0.0.0.0 --port 8000     # OpenAPI at /docs
```

| Endpoint | Does |
| --- | --- |
| `POST /api/v1/score` | score named accounts, with explanations |
| `POST /api/v1/score-all` | score a whole reference date |
| `GET /api/v1/model` | what is serving, and its threshold |
| `GET /api/v1/economics` | the numbers behind the threshold |
| `GET /health` | liveness, database, whether a model is loaded |
| `POST /admin/reload` | pick up a newly promoted model |

The API scores accounts **that already have features in the store**; it does not
accept a feature vector from the network. That was a deliberate choice: a caller
cannot invent an account or probe the decision boundary one crafted request at a
time.

Explanations are **group-based**. Per-feature perturbation was tried first and
produced sign-flipped explanations, because setting one feature of a correlated
group to its median creates a row that cannot exist — eight active users and
zero sessions — which the model scores as *more* risky. Perturbing the whole
group keeps the row coherent and answers the question a CSM is actually asking.

Every prediction is stored with its probability, decision, **the threshold that
produced it**, expected value, explanation and measured latency. Without the
threshold on the row, precision measured later would silently use today's
threshold against yesterday's decisions.

## Monitoring

A model that predicts 60 days ahead cannot be scored for 60 days, so there are
two monitors and neither replaces the other.

**Drift, available immediately.** PSI per feature against bins frozen from the
training distribution and stored in `ml.drift_baseline`. Freezing is the part
that is usually wrong: re-binning each period independently compares two sets of
deciles, which both hold 10 % by construction, and reports approximately zero
drift no matter what happened. Current data: `open_tickets` 0.308 (`ALERT`),
`tenure_days` 0.178 (`WARN`), `days_since_nps` 0.137 (`WARN`) — all true
positives with unexciting causes, which is what honest drift monitoring mostly
looks like.

**Live performance, one horizon late.** `polaris monitor` joins predictions to
the labels that have since arrived and reports PR-AUC, precision and recall *at
the threshold that was used*, plus realised value in euros. Predictions still in
flight are counted and named rather than implied.

Prediction drift compares the two most recent scoring runs **by reference
date**. The first implementation compared wall-clock windows, which put every
prediction from a backfill into the same window and reported a confident zero
where the truth was "there is nothing to compare" — an integration test now
asserts the one-batch case reports its own uselessness.

Details and what would page someone: [`docs/monitoring.md`](docs/monitoring.md).

## Testing

```bash
make test               # unit tests, no database
make test-integration   # everything (needs PostgreSQL)
make check              # lint + types + unit tests, which is what CI's first job runs
```

**71 tests**, all passing locally and in CI on Python 3.11 and 3.12.

The unit tests cover the feature contract's coherence, the economics arithmetic,
the leakage screens (including a regression test for the renewal-date bug) and
the metrics and PSI implementations. The integration tests use a real PostgreSQL
and a small real simulated business, because what is worth testing here is the
point-in-time SQL, the temporal split and the gate — all of which a mock would
simply agree with.

The ones I would point at in an interview:

- rebuilding a past reference date after new data arrives changes nothing;
- a ticket closed after the reference date still counts as open on it;
- no `(account, date)` pair appears in two splits, and the embargo is at least
  one horizon;
- a stricter segment rule blocks a model that is better overall;
- `--force` overrides the gate **and records why**;
- exactly one version is in production after a promotion cycle;
- prediction drift says when it cannot compare, instead of reporting zero.

No badge in this README claims a coverage percentage, and none claims the tests
pass — the CI badge at the top reports that, and it reports it honestly.

| Job | Does |
| --- | --- |
| **lint** | Ruff lint, Ruff format check, mypy |

| **lifecycle** | the whole pipeline end to end, asserting the documented properties |
| **docker** | builds the image and smoke-tests it, including non-root |

The lifecycle job is the interesting one. It does not check that commands exit
zero; it asserts the properties this README claims:

- the most recent reference date carries features and **no labels**;
- the leakage screens report no leak;
- a challenger that cannot beat its champion is refused **with exit code 3**;
- after the refusal, the incumbent is still the serving model;
- every prediction is logged with exactly one model version and its threshold;
- exactly one version is in production after the cycle;
- the API's `decision` equals `probability >= threshold` for every prediction it
  returns.

## Results

Measured on the simulated business, seed `20260301`. Reproduce with the commands
in section 10.

**The data.** 3 000 accounts, 24 months, 1 702 486 usage rows, 44 414 tickets,
54 108 invoices; 739 accounts churned (24.63 %). Feature store: 104 849 rows over
46 fortnightly reference dates, 95 774 labelled, base rate **2.77 %**.

**The models** (test split: 20 874 rows, 611 churns):

| Metric | v1 logistic | v2 gradient boosting |
| --- | --- | --- |
| PR-AUC | 0.2856 | **0.3155** |
| ROC-AUC | 0.8859 | 0.8856 |
| Brier | 0.0242 | 0.0236 |
| Lift @ top 100 | 23.2× | 28.4× |
| Threshold | 0.0935 | 0.1162 |
| p95 latency | 15.8 ms | 25.7 ms |

**By segment:** smb 0.3012 → 0.3487, mid_market 0.2629 → 0.2392, enterprise
0.2686 → 0.2548 (4 churns, not evaluable).

**After the fact**, on 2 314 predictions whose labels have since arrived (74
churns, 2 261 still pending): PR-AUC 0.199, precision 0.211, recall 0.324 at the
threshold used, realised value **24 900 €**.

Live PR-AUC is well below the test figure, and that gap is reported rather than
smoothed away: one fortnightly batch with 74 positives is a much smaller and
noisier sample than a four-month test split. It is the number a reviewer should
want to see.

[`docs/model-card.md`](docs/model-card.md).

## Limitations

Named, because a portfolio project that hides them is less convincing than one
that does not:

- **The data is simulated.** The relationships are the ones the generator was
  written with. The claim of this project is about the pipeline, not the model
  quality.
- **Enterprise accounts are not evaluable** at this volume — and they are worth
  the most. More data for that segment is the only fix.
- **No shadow deployment.** A challenger is judged on a held-out test split, not
  by scoring alongside the champion for two weeks. That is the right next step.
- **No automated retraining trigger.** Drift raises a status; a human decides.
- **Fairness is checked across `segment` only.** Country and industry are
  features with no per-group check.
- **No API authentication, no secret manager, no artefact signing.** See
  [`docs/security.md`](docs/security.md), which names every control that is
  missing as well as the ones that are there.
- **Explanations are local sensitivity, not Shapley values.** Honest reason: group
  perturbation is something I can explain end to end.

### Future improvements

Shadow scoring for two weeks before promotion; per-segment calibration checks;
a survival model for comparison, which handles censoring instead of picking a
horizon; an approval workflow in place of `--force`; retention policy and
deletion path for predictions; Azure deployment (Container Apps + PostgreSQL
Flexible Server + Key Vault) with the artefact store outside the image.

### Security

No credential in the repository, `SecretStr` for the password, `safe_dsn` in every
log line, bound parameters everywhere with an allow-list for the one thing that
cannot be bound (schema names), non-root container, and an honest list of what is
not implemented. Full detail: [`docs/security.md`](docs/security.md).
