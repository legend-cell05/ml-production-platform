# Architecture

> Synthetic data throughout. "Vertex Systems" is a simulated B2B SaaS company
> generated by `polaris simulate`; no real customer, account or invoice exists
> in this repository.

The platform answers one question on a fortnightly cadence: **which accounts
are likely to churn within the next 60 days, and which of them is it worth
spending a retention play on?** Everything below exists to make that answer
reproducible, auditable, and safe to act on.

---

## 1. The shape of it

```
                          ┌──────────────────────────────┐
                          │  saas.*   (simulated source) │
                          │  account, subscription,      │
                          │  usage_daily, ticket,        │
                          │  invoice, nps, event         │
                          └───────────────┬──────────────┘
                                          │  sql/features/build_features.sql
                                          │  one execution per reference date
                                          ▼
                          ┌──────────────────────────────┐
   feature contract  ───▶ │ features.churn_features      │
   (definitions.py)       │ PK (reference_date,          │
                          │     account_id)              │
                          │ 33 features + label +        │
                          │ label_known_at               │
                          └───────────────┬──────────────┘
                                          │  data/dataset.py
                                          │  temporal split + embargo
                    ┌─────────────────────┼─────────────────────┐
                    ▼                     ▼                     ▼
             leakage screens        training pipeline      economics
             features/leakage.py   training/*.py          economics.py
                    │                     │                     │
                    │              MLflow (params,              │
                    │              metrics, artefacts)          │
                    │                     ▼                     │
                    │           ┌──────────────────────┐        │
                    └──────────▶│ ml.model_version     │◀───────┘
                                │ registry + stages    │
                                └──────────┬───────────┘
                                           │  promotion gate (6 checks)
                                           ▼
                    ┌────────────────────────────────────────┐
                    │ serving (FastAPI)   monitoring          │
                    │ /api/v1/score       PSI drift           │
                    │ /api/v1/score-all   label-lagged        │
                    │ → ml.prediction     performance         │
                    └────────────────────────────────────────┘
```

Four schemas, three of them ours:

| Schema | Holds | Written by |
| --- | --- | --- |
| `saas` | the simulated business | `polaris simulate` |
| `features` | the point-in-time feature store | `polaris build-features` |
| `ml` | training runs, registry, predictions, evaluation, drift baselines | training, promotion, serving, monitoring |

The schema names are configuration (`POLARIS_SOURCE_SCHEMA`, and so on) and are
validated against `[a-z_][a-z0-9_]*` before they are ever interpolated into
SQL; a schema name cannot be a bound parameter, so the allow-list is the
control.

---

## 2. Why the feature store is a table and not a query

The naive design computes features inside the training script. It works until
the first time serving needs the same numbers, at which point there are two
implementations of `usage_trend_28d_vs_90d` and they disagree.

Here there is one implementation — `sql/features/build_features.sql` — executed
once per reference date, and everything downstream reads rows. Training,
scoring, drift monitoring and the notebooks all see the same values, because
they are the same values.

The cost is a migration whenever a feature is added, and a `FEATURE_VERSION`
that has to be bumped in step with the SQL. That friction is deliberate: a
feature nobody can name is a feature nobody can explain to the customer success
manager who asks why their account was flagged.

---

## 3. Point-in-time correctness

This is the property the rest of the system is built to protect. Every row in
the feature store answers: *what was knowable about this account on this date?*

Three mechanisms enforce it:

1. **Strict inequality on every date comparison in the SQL.** `< :reference_date`
   everywhere, never `<=`. A ticket opened on the reference date itself is not
   knowable at the start of that day.
2. **`days_to_renewal` is computed, not looked up.** The obvious version reads
   the subscription's renewal date — which, in the source system, is only
   populated for accounts that went on to renew. That single column took the
   first model to a ROC-AUC of 0.995. It is now derived from `signup_date` plus
   the contract term, by anniversary arithmetic, which is what a system would
   actually know on the day.
3. **`label_known_at`.** The label is `NULL` until `reference_date + horizon`
   has actually elapsed in the simulated world. The most recent 60 days of the
   store therefore carry features and no label — not a gap to be filled, but
   the honest state of the world, and the reason the training set stops where it
   does.

`docs/features.md` covers the contract itself; the leakage screens that check
this empirically are in `docs/training.md`.

## 4. Layers

| Layer | Module | Responsibility |
| --- | --- | --- |
| Configuration | `config.py` | typed settings, `SecretStr`, derived economics |
| Generation | `generation/simulator.py` | the simulated business, with a latent health process |
| Features | `features/definitions.py`, `features/leakage.py` | the contract; the screens that test it |
| Data | `data/dataset.py` | temporal split, embargo, fingerprint |
| Economics | `economics.py` | break-even probability, threshold choice |
| Training | `training/pipelines.py`, `training/evaluate.py`, `training/train.py` | pipelines, metrics, MLflow, run records |
| Registry | `registry/store.py`, `registry/promotion.py` | versions, stages, the six-check gate |
| Serving | `serving/*` | FastAPI, in-process predictor, group explanations |
| Monitoring | `monitoring/drift.py`, `monitoring/performance.py` | PSI against a frozen baseline, label-lagged performance |
| Orchestration | `pipeline.py`, `cli.py` | the operations, and one command each |

`pipeline.py` is the only module that composes the others. The CLI contains no
logic: if a command needs a decision made, the decision belongs upstream.

---

## 5. The model is loaded once, in-process

Serving deliberately does not call a model server. The predictor loads the
production artefact at startup, and `POST /admin/reload` swaps it. For a
fortnightly batch of a few thousand accounts, a network hop to a separate
inference service buys nothing and adds a failure mode; p95 latency measured on
the test sample is 25.7 ms, inside a 50 ms budget that the promotion gate
enforces.

This becomes the wrong choice the moment scoring needs a GPU, or the moment two
services need the same model — at which point the artefact is already in the
registry and the change is where it is loaded, not how it was trained.

---

## 6. What a full cycle does

```
polaris simulate        # generate the business (24 months, 3 000 accounts)
polaris build-features  # one execution of the SQL per reference date
polaris screen          # leakage screens; a LEAK verdict is a non-zero exit
polaris train --promote  # train, register, evaluate the gate, ship if it passes
polaris score           # score the latest reference date, log every prediction
polaris monitor         # PSI drift now; performance once labels have matured
```

Exit codes: `0` success, `1` handled failure, `2` misuse, `3` blocked by a gate.
The last is separate on purpose — a refused promotion is not a crash, and a
scheduler must be able to tell the difference without parsing text.

---

## 7. Deliberate limits

- **One model, one problem.** The horizon is configuration, but changing it
  changes the label, so a model trained under a different horizon is a
  different model and the registry will not serve it under this one.
- **No feature backfill service.** Rebuilding is a full recompute; at this data
  volume it takes under a minute and an incremental path would be untested
  complexity.
- **No online features.** Everything is computed from data that lands daily.
  Anything needing sub-day freshness is outside the design.
- **The container images have never been built in this environment** (no Docker
  daemon available); CI builds and smoke-tests them on every push.
